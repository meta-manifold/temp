# Intel 스칼라 GEMM의 타일 · split 선택: 비용 모델 보정

이 문서는 **Intel GPU에서 Linear가 빠른 타일과 split을 고르도록, 비용 모델의 상수를 측정으로 정하는 작업 안내서**다.
대상은 `linear-tile-intel.comp`의 fp16 누적 경로다. fp32 누적 경로는 다루지 않는다.
`linear.h`는 지금 이 비용 모델 대신 6번 문서의 구조 규칙(S8)을 쓴다.

Linear는 입력 크기에 따라 타일 5개와 split 최대 5개 중 하나를 고른다. 모델을 실행할 때마다 최대 25개 조합을 모두
시험하면 선택 자체에 시간이 많이 든다. 대신 각 조합의 비용을 식으로 계산해 가장 작은 것을 고른다. 여기서 **보정**은
그 식에 들어가는 상수를 미리 측정해 정하는 것을 뜻한다. 셰이더 알고리즘을 새로 만드는 작업과는 구분한다.

처음 작업한다면 다음 순서로 읽고 실행한다. 2절은 기본 개념과 실행 후보, 3절은 비용 모델을 설명한다. 실제 작업은 4절부터 순서대로 진행한다.
새 타일을 추가하거나 후보 설정을 바꿀 때는 부록 A를, 측정 조건과 모델의 한계는 부록 B를, Linear가 실행 때 타일과 split을 고르는 흐름은 부록 C를, 비용 식의 버전별 변화는 부록 D를, pi0.5 층별 최선 설정은 부록 E를 참고한다.

| 순서 | 할 일 | 완료했을 때 남는 것 |
|---|---|---|
| 1 | 환경과 셰이더를 확인하고 Release로 빌드한다(4절) | 측정용 실행 파일, 데모 실행 파일 |
| 2 | 측정 설계를 확인하고 형상을 생성·측정한다(5 ~ 6절) | `shapes.json`, 카테고리별 `.out`, `run.log` |
| 3 | 상수를 맞추고 채택 기준을 확인한다(7 ~ 8절) | 보정 상수, 선택 손실, 채택 여부 |
| 4 | 확정한 식과 상수를 Linear에 이식하고 선택 결과를 확인한다(9절) | 수정한 `linear.h`, 빌드 및 선택 일치 확인 |

명령은 별도 표시가 없으면 **저장소 루트에서 PowerShell로 실행**한다. 아래 경로는 기본 빌드 폴더가 `build/`인 경우다.

## 1. 목적

- **선택 품질:** 형상마다 실측 최선의 (타일, split)에 가깝게 고른다. 목표는 실제 모델 형상에서 실측 최선 대비 평균 손실
  3% 이하, 최대 15% 이하다.
- **환경 차이의 영향 줄이기:** 비용 식은 공식 스펙(Xe-core 수, 코어당 HW스레드), 타일별 측정 시간 `w_t`, 무차원
  계수로 구성한다. 메모리 대역폭처럼 PC마다 달라지는 절대값은 직접 넣지 않는다. 모든 GPU에 같은 상수를 쓰겠다는 뜻은
  아니며, GPU 세대나 커널이 바뀌면 다시 보정한다.
- **재현성:** 형상 생성, 측정, 상수 맞추기를 스크립트로 고정한다. 측정 잡음 때문에 상수가 완전히 같아지지는 않더라도,
  다시 측정했을 때 비슷한 선택 품질이 나오는 것을 목표로 한다.

## 2. 기본 개념과 실행 후보

비용 모델이 고르는 것은 **주어진 형상에서 사용할 타일과 split의 조합**이다. 후보는 아래 표의 타일 5개와
split 1 · 2 · 4 · 8 · 16이며, K 길이에 따라 사용할 수 없는 split은 제외한다. 먼저 이를 이해하는 데 필요한 용어를 설명한다.

### 2.1 먼저 알아둘 용어

Linear의 곱셈은 `I[M, K] × W[N, K]ᵀ → O[M, N]`이다. M은 입력 행 수, N은 출력 열 수, K는 각 출력 원소를 구할 때
곱해서 더하는 길이다. **본문의 형상 표기는 `(M, N, K)`지만, 하네스의 `-shape`와 Python 데이터는 `(M, K, N)` 순서**다.
예를 들어 `-shape 768,1152,2048`은 M=768, K=1152, N=2048이다.

- **타일:** 워크그룹 하나가 맡는 출력의 직사각형 영역이다. 큰 타일은 데이터를 재사용하기 좋지만, 작은 출력에서는
  워크그룹 수가 부족하거나 타일의 빈 부분이 늘 수 있다.
- **워크그룹 / subgroup:** 함께 실행되는 invocation 묶음이다. 여기서는 subgroup 하나가 16개 lane으로 구성된다.
  `wgSize=128`인 워크그룹에는 subgroup이 8개 있다.
- **웨이브:** 이 모델에서는 Xe-core 하나가 한 번에 처리하는 워크그룹 묶음을 뜻하며, 최대 `cap`개까지 담는다.
  예를 들어 한 코어가 한 번에 8개를 처리할 수 있다면(`cap=8`), 10개를 맡았을 때는 8개와 2개, 두 웨이브로 계산한다.
- **epilogue:** 행렬 곱셈 뒤에 적용하는 bias, residual, 활성화, scale 연산이다.

### 2.2 split과 epilogue

워크그룹 하나가 출력 O의 wgM × wgN 타일을 계산하고, K를 8칸씩 공유 메모리에 올려 누적한다.
- **split s:** K를 s조각으로 나눠 워크그룹을 s배로 늘린다. 각 조각은 partial을 메모리에 쓰고, reduce 패스가 이를 더한다.
- **epilogue:** bias · residual · 활성화 · scale은 reduce 패스가 처리한다. 그래서 split 1이어도 epilogue가 있으면 reduce
  패스가 돈다. split 1이고 epilogue가 없으면 타일 커널이 출력에 바로 쓴다.

### 2.3 현재 사용하는 후보

| 타일 (wgM × wgN) | wgSize | tM | tN | SGN | 코어당 동시 워크그룹 (cap) | lane당 누산기 / W 캐시 |
|---|---|---|---|---|---|---|
| 32 × 64 | 128 | 4 | 4 | 1 | 16 | 16 / 32 |
| 64 × 96 | 128 | 8 | 6 | 1 | 16 | 48 / 48 |
| 96 × 128 | 256 | 6 | 8 | 1 | 8 | 48 / 64 |
| 128 × 128 | 256 | 8 | 8 | 1 | 8 | 64 / 64 |
| 192 × 64 | 512 | 6 | 4 | 1 | 4 | 24 / 32 |

split 후보는 1, 2, 4, 8, 16이고, 한 조각의 k 길이가 64 미만(K / s < 64)이 되는 split은 뺀다. wgK는 8이다.
후보 5개는 46개 크기의 풀을 측정해 고른 결과다(부록 A.3).

## 3. 비용 모델

### 3.1 비용 식

```
cost(t, s) = w_t · work + π · w_ref · M·N·(s+1) / 4096 · [reduce 패스가 돈다]

work  = ks · (load + τ · [full ≥ 1] + ε · [full ≥ 2 그리고 rem = 0])
           · (1 + β · max(0, log2(M · ks · 4 B / L2)))
ks    = ⌈K/s⌉                           split 하나가 맡는 K 길이
tiles = ⌈M/wgM⌉ · ⌈N/wgN⌉
per   = ⌈tiles · s / 코어 수⌉            가장 바쁜 코어가 맡는 워크그룹 수
cap   = 코어당 HW스레드 / (wgSize / 16)
full  = per / cap,  rem = per % cap,  r = rem / cap
load  = full + (rem > 0 ? floor + (1 − floor) · r : 0)
π     = M·N·s·4 B ≤ L2 이면 π_in, 아니면 π_out
w_ref = w(128 × 128),  L2 = 4 MB (GPU L2)
```

여기서 `⌈x⌉`는 올림, `full = per / cap`은 **정수 나눗셈의 몫**, `%`는 나머지다. `[조건]`은 참이면 1, 거짓이면 0이다.
`w_t`는 타일 t의 단위 K 길이당 웨이브 비용이다. `cost`는 후보의 순위를 정하는 근삿값이며, 실제 시간을 정확히
재현해야 하는 값은 아니다. `4096`은 reduce 계수의 크기를 조절하는 정규화 상수이며, `π`와 함께 사용한다.

### 3.2 계산 예시

예를 들어 M=N=128, K=1024에서 128 × 128 타일을 쓰면 출력 타일은 1개다. 8코어, `cap=8`, `floor=0.485`라면:

- split 1: `per=1`, `r=1/8`, `load=0.485 + 0.515 × 0.125 ≈ 0.55`, ks는 1024이므로 연산 항은 `w_t × 1024 × 0.55`다.
- split 4: `per=1`, `load≈0.55`, ks는 256이므로 연산 항은 1/4로 줄지만 reduce 비용이 생긴다.

이처럼 split은 작은 출력에서도 일을 여러 코어에 나눌 수 있게 한다. 반대로 출력이 이미 충분히 크면 병렬성의 이득이
작아지고, partial을 쓰고 합치는 비용이 커질 수 있다. 비용 모델은 이 둘을 함께 비교한다.

### 3.3 비용 항과 보정 상수

| 항 | 뜻 |
|---|---|
| `ks · load` | 가장 바쁜 코어가 웨이브를 load번 돈다. 홀로 덜 찬 마지막 웨이브는 찬 정도에 비례하지 않고 최소 floor만큼 든다 |
| `τ · ks` | 커널 끝 꼬리. 코어가 한 번 이상 꽉 차면, 마지막에 남은 워크그룹을 기다리며 다른 슬롯이 논다. 그 시간은 워크그룹 하나 길이(ks)에 비례하고, split이 이를 줄인다 |
| `ε · ks` | 웨이브가 2개 이상의 정수로 딱 떨어질 때의 추가 비용. 모든 슬롯이 늦은 워크그룹을 함께 기다린다. 마지막 웨이브가 덜 차면 앞 웨이브의 늦은 워크그룹이 빈 슬롯에서 돌아 이 비용이 숨는다. 웨이브가 하나뿐이면 함께 시작해 함께 끝나 생기지 않는다 |
| `1 + β · max(0, log2(M · ks · 4 B / L2))` | I를 다시 읽는 비용. N 방향 타일마다 I를 다시 읽는데, split 하나가 쓰는 I(M × ks × 4 B)가 GPU L2를 넘으면 그 다시 읽기가 메모리까지 간다. split은 이 크기를 줄인다 |
| `π · w_ref · M·N·(s+1) / 4096` | reduce 패스(partial s개 읽기 + 출력 쓰기)의 비용. 128 × 128 타일의 연산 시간에 대한 비율로 나타내고, partial이 GPU L2를 넘으면 더 비싸다 |

| 상수 | 종류 | 정하는 곳 |
|---|---|---|
| 코어 수, 코어당 HW스레드, GPU L2 크기 | 공식 스펙(Core Ultra 7 155H: 8, 128, 4 MB) | 고정 |
| w_t (타일 5개) | 측정 | 7절 |
| floor, τ, ε, β, π_in, π_out | 무차원, 측정 | 7절 |

선택에는 비용의 상대적인 크기를 사용한다. 모든 w가 같은 비율로 변하고 나머지 계수가 유지되면 선택은 같다.
실제로는 연산과 메모리의 속도가 같은 비율로 변하지 않을 수 있으므로, 클럭이나 전력 조건의 영향을 완전히 없애는 식은 아니다.

## 4. 측정 도구와 준비

### 4.1 실행 환경 확인

필요한 것은 프로젝트를 빌드할 수 있는 CMake·C++·Vulkan 환경, 대상 Intel GPU, Python 3, NumPy다.
먼저 저장소의 기본 빌드 환경을 준비한다. 이 문서의 측정 스크립트는 현재 **8코어 Meteor Lake**를 기준으로 하므로,
다른 GPU에서는 `fit.py`의 `CORES`와 비용 식의 코어당 HW스레드 가정부터 확인한다.

```powershell
python --version
python -c "import numpy; print(numpy.__version__)"
```

NumPy를 찾지 못하면 사용할 Python 환경에 `python -m pip install numpy`로 설치한다.
`run.py`는 실행 파일을 `build/bin/Release/test-linear-tune-intel.exe`에서 찾는다. 다른 빌드 폴더나 단일 구성
생성기를 사용한다면 `run.py`의 `EXE`를 실제 경로에 맞춘다. `--work`는 측정 결과 경로만 바꾸는 옵션이다.

### 4.2 측정 도구: 튜닝 하네스

`test-linear-tune-intel`([main.cpp](main.cpp))은 GEMM 커널 하나를 형상과 설정을 바꿔 가며 재는 프로그램이다. 형상 하나마다
다음을 한다.
1. 무작위 I(fp32, [M, K])와 W(fp16, [N, K])를 만들어 GPU에 올린다.
2. 주어진 설정마다 타일 커널을 실행한다. split이 있거나 reduce를 요구하면 reduce 패스도 이어서 실행한다.
3. 출력 몇 행을 CPU 결과와 비교해 오차(`maxRel`)를 출력한다.
4. 실행 시간을 GPU 타임스탬프로 재서 출력한다.

**재는 커널:** 타일 커널은 [linear-tile-11.comp](linear-tile-11.comp)이다. Linear의 `linear-tile-intel.comp`와 계산 본문이 같고, 특수화 상수 두 가지만 다르다.
  - **W 패딩:** 11은 WPAD(상수 6)로 받고, Linear는 staging dtype으로 정한다(fp16 0, fp32 1칸). `calib/`의 도구는 Linear와 같은 값을 넘긴다.
  - **타일 모양:** 11은 SGN(상수 9)을 받아 wgM, wgN을 계산하고, Linear는 wgM, wgN(상수 2, 3)을 받아 SGN을 계산한다.

측정 전에 두 파일의 차이가 주석과 이 두 가지뿐인지 확인한다.

```powershell
git diff --no-index vai/shaders/linear-tile-intel.comp tests/linear-tune-intel/linear-tile-11.comp
```

reduce 패스는 하네스의 [split-reduce.comp](split-reduce.comp)이다. Linear의 `linear-reduce.comp`에서 bias · residual · 활성화 · scale을
뺀 것과 같은 방식으로 접는다. invocation 하나가 연속한 네 원소를 vec4로 읽고, 워크그룹은 256 invocation이다.
그래서 reduce를 거치는 설정의 시간은 epilogue가 없는 층에서 Linear가 쓰는 시간과 같다.

**partial 버퍼는 형상마다 하나:** 한 형상의 설정들은 차례로 하나씩 돌므로, 하네스는 그 형상에서 가장 큰 split에 맞춘 partial
버퍼 하나를 모든 설정이 함께 쓴다. 설정마다 따로 만들어 모두 살려 두면 출력이 큰 형상에서 수 GB가 되어 내장 GPU가 쓰는
메모리가 모자라고, 버퍼가 밀려나면서 일부 설정이 몇 배 느리게 재진다.

**빌드:** 기존 `build/`의 생성기 설정을 유지하면서 테스트와 예제를 켜고, 두 타깃을 Release로 빌드한다.

```powershell
cmake -S . -B build -DVAI_BUILD_TESTS=ON -DVAI_BUILD_EXAMPLES=ON
cmake --build build --config Release --target test-linear-tune-intel demo-pi05
Test-Path build/bin/Release/test-linear-tune-intel.exe
```

빌드가 성공하고 마지막 출력이 `True`인지 확인한다. 측정이 끝날 때까지 셰이더를 바꾸지 않는다.

### 4.3 설정 문자열

하네스는 설정 하나를 쉼표로 이은 14칸 문자열로 받는다. 이 보정에서는 아래 값만 쓴다.

| 칸 | 이름 | 쓰는 값 | 뜻 |
|---|---|---|---|
| 1 | shader | 11 | `linear-tile-11.comp` |
| 2 | wgSize | 표의 값 | 워크그룹 invocation 수(부록 A.1) |
| 3 | sgSize | 16 | subgroup 크기. 파이프라인에 이 크기를 강제한다 |
| 4 | tN | 표의 값 | lane당 출력 열 수 |
| 5 | tM | 표의 값 | subgroup당 출력 행 수 |
| 6 | order | 0 또는 1 | 워크그룹 실행 순서. 0은 디스패치 x축이 M 타일, 1은 N 타일 |
| 7 | SGN | 표의 값 | N 방향 subgroup 수 |
| 8 | wgN | 0 | 자리만 채움(하네스가 wgSize · SGN · tN으로 계산) |
| 9 | wgK | 8 | k 블록 크기 |
| 10 | WPAD | 0 | 공유 메모리 W 패딩. Linear와 같게 fp16 staging은 0, fp32 staging은 1 |
| 11 | acc | 1 | fp16 누적(0이면 fp32) |
| 12 | reqSg | 0 | 자리만 채움(sgSize를 씀) |
| 13 | opt | 0 ~ 16 | 0이면 split 1, reduce 없음. 1 이상이면 그 값이 split 수이고 reduce 패스를 항상 돈다 |
| 14 | stage32 | 0 | fp16 스테이징(1이면 fp32) |

**order 정하는 법:** Linear가 쓰는 순서와 같게 둔다. Linear는 타일이 더 많은 바이트를 읽는 쪽 피연산자를 이웃 워크그룹이
공유하도록 순서를 정한다. I fp32 · W fp16에서는 wgM × 4 > wgN × 2이면 0, 아니면 1이다.

5타일의 split 1(reduce 없음) 설정 문자열은 다음과 같다. split과 reduce를 바꿀 때는 13번째 칸만 바꾼다.

| 타일 | 설정 문자열 |
|---|---|
| 32 × 64 | `11,128,16,4,4,1,1,0,8,0,1,0,0,0` |
| 64 × 96 | `11,128,16,6,8,0,1,0,8,0,1,0,0,0` |
| 96 × 128 | `11,256,16,8,6,0,1,0,8,0,1,0,0,0` |
| 128 × 128 | `11,256,16,8,8,0,1,0,8,0,1,0,0,0` |
| 192 × 64 | `11,512,16,4,6,0,1,0,8,0,1,0,0,0` |

### 4.4 시간을 재는 방식

명령줄 예:
```
build/bin/Release/test-linear-tune-intel.exe -passes 9 -flush -shape 768,1152,1152 11,256,16,8,8,0,1,0,8,0,1,0,0,0 11,256,16,8,8,0,1,0,8,0,1,0,4,0
```
형상 768 × 1152 × 1152에서 128 × 128의 split 1(reduce 없음)과 split 4를 잰다.

위 명령은 측정 방식을 보여주는 예시다. 실제 보정에서는 `run.py`가 형상과 설정별로 이런 명령을 자동 실행하고 결과를
파일에 저장하므로, 직접 입력할 필요는 없다. 실행 방법은 [6절 측정 실행](#6-측정-실행)을 참고한다.

| 옵션 | 뜻 |
|---|---|
| `-shape M,K,N` | 잴 형상. 여러 번 줄 수 있고, 형상마다 뒤의 모든 설정을 잰다 |
| `-passes 9` | 형상의 설정들을 9바퀴 돌며 번갈아 잰다. 바퀴마다 순서를 바꾸고(정순, 역순, 무작위), 바퀴 0은 예열로 버리고 1 ~ 8의 중앙값을 쓴다. 클럭 변동이 설정들에 고르게 섞인다 |
| `-flush` | 실행마다 앞에 32 MB 복사를 넣어 GPU L2(4 MB)를 비우고, 그 실행만 타임스탬프로 잰다. 한 번 방문에 합계 약 10 ms가 되도록 3 ~ 16회 재서 평균한다. 층마다 다른 가중치를 처음 읽는 모델의 실제 조건이다 |

**측정 횟수:** 형상 × 설정 하나마다 예열 1회와 확인용 1회(오차와 첫 시간 출력)를 먼저 돌린 뒤, 바퀴마다 R회를 잰다.
R은 형상마다 설정들 첫 시간의 중앙값으로 약 10 ms를 채우는 횟수이고 3 ~ 16 사이다(`-flush`). 한 번 실행에서 커널을 돌리는 횟수는 다음과 같다.

```
형상 수 × 설정 수 × (2 + 패스 수 × R)
```

예를 들어 128 × 128이 약 0.5 ms인 형상 하나에 설정 하나를 `-passes 9`로 재면 R = 16이고, 2 + 9 × 16 = 146회를 돈다.

출력에서 쓰는 줄은 `pass <바퀴>  <설정 이름> … <시간> ms`이다. 설정 이름의 `tile<wgM>x<wgN>`으로 타일을, `opt<값>`으로 split을 읽는다. `opt`가 없으면 split 1, reduce 없음이다.

## 5. 측정 설계

### 5.1 카테고리

측정은 목적이 다른 열 개 카테고리로 나눈다. 한 조합은 (형상, 타일, split, reduce 여부) 하나이고, 하네스 설정 문자열 하나에 해당한다.
학습에는 grid · gridsplit · split · full · wave · focus를, 평가에는 val · val2 · test를 쓴다. pairs는 reduce 비용을 따로 확인하는 용도다.

| 카테고리 | 형상 수 | 형상 만드는 법 | 타일 | split | reduce | 총 조합 수 | 목적 |
|---|---|---|---|---|---|---|---|
| grid | 100 | 로그 균등 추출(시드 1).<br>M: 32 ~ 4096, N: 128 ~ 32768, 둘 다 16 단위.<br>K: 256 ~ 16384, 128 단위. | 5종 전부 | 1 | 없음 | 500<br>= 100 × 5 × 1 | 타일별 비용 w_t의 기준값 |
| gridsplit | 100 | grid와 동일 | 32 × 64, 192 × 64 | 2, 4, 8, 16 | 있음 | 678<br>= 100 × 2 × 4 − 122 | 코어당 워크그룹 16개 · 4개 타일의 split 효과 |
| split | 300 | 128 × 128 타일 수 T(22종), K(7종), 목표 비율 N/M(5종)을 값마다 고르게 조합(시드 2). M · N은 128의 배수 | 128 × 128 | 1, 2, 4, 8, 16 | split 1: 없음·있음 각각<br>split ≥ 2: 있음 | 1,665<br>= 300 × 1 × 6 − 135 | 코어를 채우는 정도와 K 길이에 따른 split 효과 |
| full | 150 | grid와 같은 분포(시드 5). 앞 카테고리와 겹치는 형상은 건너뜀 | 5종 전부 | 1, 2, 4, 8, 16 | split 1: 없음·있음 각각<br>split ≥ 2: 있음 | 4,115<br>= 150 × 5 × 6 − 385 | 모든 타일 × 모든 split. 타일과 split이 얽힌 판단 |
| wave | 120 | 타일마다 워크그룹 수를 웨이브 0.75, 1, 1.25, 1.5, 2, 2.5, 3, 4개가 되게 정하고(5타일 × 8 × K 3종), M · N은 타일 경계에서 조금 비켜 둠(시드 6) | 5종 전부 | 1, 2, 4, 8, 16 | 위와 같음 | 3,400<br>= 120 × 5 × 6 − 200 | 정수 웨이브와 덜 찬 마지막 웨이브의 비용 |
| focus | 100 | 실제 형상 하나(922 × 2048 × 2048) 주변. M 800 ~ 1056의 정수, K · N 1536 ~ 2560(시드 7). 중심 형상은 뺌 | 5종 전부 | 1, 2, 4, 8, 16 | 위와 같음 | 3,000<br>= 100 × 5 × 6 | 식이 특정 형상에서 놓치는 요인 찾기 |
| pairs | 30 | 규칙으로 만든 목록. K=1024. M·N을 2^14 ~ 2^25에서 로그 간격으로, N/M은 1, 4, 1/4 순환 | 128 × 128 | 1 | 없음·있음 각각 | 60<br>= 30 × 1 × 2 | reduce 비용 확인(상수 맞추기에는 쓰지 않음) |
| val | 25 | grid와 같은 분포(시드 3) | 5종 전부 | 1, 2, 4, 8, 16 | split 1: 없음·있음 각각<br>split ≥ 2: 있음 | 705<br>= 25 × 5 × 6 − 45 | 처음 보는 형상의 선택 손실 |
| val2 | 100 | grid와 같은 분포(시드 4). 앞 카테고리와 겹치는 형상은 건너뜀 | 5종 전부 | 1, 2, 4, 8, 16 | 위와 같음 | 2,745<br>= 100 × 5 × 6 − 255 | val을 보강한 평가 |
| test | 24 | pi0.5·gemma3의 실제 형상과 층별 epilogue 여부 | 5종 전부 | 1, 2, 4, 8, 16 | 위와 같음 | 690<br>= 24 × 5 × 6 − 30 | 실제 모델 형상의 선택 손실 |

총 조합 수 = 형상 수 × 타일 수 × (split · reduce 경우 수) − 제외 조합 수다. split · reduce 경우 수는 grid 1(split 1, reduce 없음),
gridsplit 4(split 2, 4, 8, 16), pairs 2(split 1의 reduce 없음 · 있음), 나머지 6(split 1의 reduce 없음 · 있음, split 2, 4, 8, 16)이다.
제외 수는 시드로 뽑힌 형상에서 센 값이고, `gen.py`가 카테고리마다 총 조합 수를 출력한다. 열 카테고리를 합하면 17,558조합이다.

### 5.2 샘플 설계 원칙

- **M · N은 16 단위:** 128의 배수로만 재면 128 폭 타일만 패딩이 없어 유리해지고, 96 · 192 폭 타일의 패딩 비용을 배울 수 없다.
  split 카테고리만 128 × 128 타일의 split 연구라서 128의 배수를 유지한다.
- **모든 타일 × 모든 split을 재는 학습 카테고리(full)를 둔다:** split을 128 × 128과 두 타일에서만 재면, 나머지 타일의 split 판단은
  측정 없이 외삽된다.
- **현상을 일부러 담는 카테고리(wave)를 둔다:** 정수 웨이브처럼 무작위 추출에서는 드물게 나오는 경우는, 그 경우가 되도록 형상을
  설계해 재야 항을 맞출 수 있다.
- **focus는 예외적으로 쓴다:** 실제 형상 하나에서 식이 크게 틀릴 때, 그 주변 형상으로 놓친 요인을 찾는다. 찾은 항은 val · val2에서
  나빠지지 않을 때만 채택한다. 중심 형상의 test 결과는 그 뒤로 독립적인 평가가 아니다.

### 5.3 제외 조건과 형상 범위

- **제외 조합:** split s가 2 이상인 조합 중 다음 둘은 뺀다. 표의 총 조합 수는 뺀 뒤의 수다.
  - **K / s < 64:** split 하나가 맡는 K가 64보다 짧으면 split할 이유가 없다. 예를 들어 K 256은 split 4까지만, K 512는 split 8까지만 잰다.
  - **partial이 1 GiB 초과:** partial(M·N·s × 4 B)이 1 GiB(2^30 B)를 넘는 조합이다.
- **추가 크기 제한:** grid 계열 생성기는 `M·N·K ≤ 2^36`, `M·N·16·4 ≤ 1 GiB`도 적용한다.
- **규모:** 17,558조합 × 9바퀴, 약 80분이다.

## 6. 측정 실행

### 6.1 스크립트 실행 흐름

5.1절의 측정은 **형상 생성 → 시간 측정 → 상수 보정·평가** 순서로 진행한다.
[gen.py](calib/gen.py)가 형상 생성을, [run.py](calib/run.py)가 측정을, [fit.py](calib/fit.py)가 보정과 평가를 담당한다.
파일은 모두 같은 작업 폴더에 저장한다. 기본 경로는 Git 추적 대상에서 제외된 `build/calib/`다.

1. **`gen.py` — 측정할 형상 목록 생성**
   5.1절의 규칙에 따라 카테고리별 형상을 만들고 `shapes.json`에 저장한다. 난수 시드가 고정되어 있어 매번 같은 목록이 나온다.
   gridsplit은 grid의 목록을 공유하고, test는 스크립트에 미리 적힌 실제 모델 형상을 사용한다. val2 · full · wave는 앞 카테고리에서
   이미 뽑힌 형상을 건너뛴다.

2. **`run.py` — 각 조합의 실행 시간 측정**
   `shapes.json`을 읽고 grid → pairs → gridsplit → split → full → wave → focus → val → val2 → test 순으로 측정한다.
   타일·split·reduce 조합은 5.1절 표에 따라 자동으로 구성하므로 설정 문자열(4.3절)을 직접 작성할 필요가 없다.
   설정 목록이 같은 형상을 최대 8개씩 묶어 하네스를 `-passes 9 -flush`로 실행하고, 결과를 카테고리별 파일에 이어 쓴다
   (예: `grid.out`, `pairs.out`).

3. **`fit.py` — 측정 결과로 상수 보정 및 선택 품질 평가**
   카테고리별 `.out` 파일을 읽어 비용 모델의 상수를 구하고, 그 상수로 빠른 조합을 잘 고르는지 평가한다.
   카테고리별 용도와 상수를 구하는 방법은 7절에서 설명한다.

### 6.2 먼저 짧게 동작 확인

본 측정 전에 카테고리별 첫 형상만 실행해 경로와 실행 환경을 확인한다. 시험 결과가 본 측정과 섞이지 않도록 별도 폴더를 쓴다.

```powershell
python tests/linear-tune-intel/calib/gen.py --work build/calib-smoke
python tests/linear-tune-intel/calib/run.py --work build/calib-smoke --limit 1
```

| 옵션 | 쓰는 스크립트 | 뜻 |
|---|---|---|
| `--work <폴더>` | gen.py, run.py, fit.py | 작업 폴더. `shapes.json`, `<카테고리>.out`, `run.log`를 이 폴더에 쓰고 읽는다. 생략하면 `build/calib/` |
| `--limit <N>` | run.py | 카테고리마다 `shapes.json` 목록의 앞 N개 형상만 잰다. 생략하거나 0이면 전부 잰다 |

여기서는 시험용 폴더 `build/calib-smoke`에 전체 형상 목록을 만든 뒤, 카테고리마다 첫 형상 하나씩, 모두 열 형상만 잰다.

열 카테고리의 `missing`이 모두 0이고 `build/calib-smoke/run.log`의 exit 코드가 모두 0인지 확인한다.
이 데이터는 실행 확인용이므로 상수 보정에는 사용하지 않는다.

### 6.3 본 측정

새 측정은 비어 있는 작업 폴더에서 시작한다. 기본 폴더에 이전 데이터가 있다면 `--work build/calib-session-01`처럼
새 폴더를 지정하고, 이후 `gen.py`, `run.py`, `fit.py`에 같은 `--work`를 전달한다. `gen.py`는 기존 `.out` 파일을 지우지 않는다.

```powershell
python tests/linear-tune-intel/calib/gen.py      # build/calib/shapes.json
python tests/linear-tune-intel/calib/run.py      # build/calib/<카테고리>.out, run.log
```

- **한 세션에 전부 잰다:** 세션이 다르면 GPU 클럭과 온도가 달라 절대 시간이 통째로 몇 % 달라지고, 그 차이가 상수에 섞인다.
  `run.py`는 열 카테고리를 이어서 잰다. 다른 세션의 데이터와 섞지 않는다.
- **측정 중에는 다른 GPU 작업을 하지 않는다.**
- **하네스는 최대 8형상씩 부른다:** 한 번에 형상을 많이 넣으면 하네스가 중간에 끝날 수 있다. 카테고리마다 빠진 형상 수가
  출력되고, `run.py`를 다시 실행하면 완료로 판정되지 않은 형상을 이어서 잰다. 현재 완료 판정은 형상 블록에 `pass 8`이 있는지
  확인하는 방식이므로, 모든 설정의 정상 완료까지 보장하지는 않는다.
- **중단 후 재개:** 같은 측정 조건에서 잠깐 중단한 경우에만 이어서 잰다. GPU 작업이나 온도·전력 조건이 크게 바뀌었다면
  새 작업 폴더에서 전체를 다시 측정한다. 스크립트가 자동으로 세션 차이를 감지하지는 않는다.

### 6.4 보정 전에 확인할 결과

| 확인 대상 | 정상 상태 | 문제가 있으면 |
|---|---|---|
| `run.py`의 카테고리별 출력 | 열 카테고리 모두 `0 shapes missing` | 로그와 `.out`을 확인하고 원인을 해결한다 |
| `run.log` | 모든 호출의 `exit 0` | 실패한 실행의 형상과 설정을 확인한다 |
| 각 `.out`의 `maxRel` | 5e-2 이하 | 정확도 문제를 먼저 해결하고 다시 측정한다 |
| 각 형상의 측정 줄 | 예정된 설정마다 pass 0 ~ 8이 있음 | 누락된 결과를 보정에 사용하지 않는다 |

`maxRel`은 CPU 기준 결과와의 오차다. 허용 오차를 벗어난 설정은 빨라도 채택할 수 없다. `run.py`는 이 기준을 자동으로
검사하지 않으며, 하네스의 표준 오류도 `.out`에 저장하지 않는다. 실패 원인이 로그에 없으면 4.4절처럼 해당 형상을 직접 실행한다.

## 7. 상수 맞추기

`fit.py`는 두 단계로 상수를 구한 뒤, 상수 맞추기에 쓰지 않은 val · val2 · test로 선택 품질을 평가한다.

| 단계 | 구하는 것 | 쓰는 카테고리 |
|---|---|---|
| 1단계 | 타일별 w_t의 기준값 | grid |
| 2단계 | 모든 상수(w_t, floor, τ, ε, β, π_in, π_out) | grid, gridsplit, split, full, wave, focus |
| 평가(8절) | 선택 손실 | val, val2, test |

```powershell
python tests/linear-tune-intel/calib/fit.py | Tee-Object -FilePath build/calib/fit.txt
```

별도 작업 폴더를 썼다면 `fit.py --work <폴더>`를 사용하고 `fit.txt`도 그 폴더에 저장한다.
먼저 `loaded:`에 표시되는 형상 수가 5.1절 표와 같은지 확인한다. 이 수는 형상 수만 확인하므로 설정별 pass 누락 여부는 6.4절에서
따로 확인해야 한다.

### 7.1 1단계: w_t의 기준값

grid(split 1, reduce 없음)에서 `시간 = w_t · K · load + c0`를 측정값으로 정규화한 최소제곱으로 맞춘다. 마지막 웨이브는 `max(r, 0.65)`로
센다. Huber 가중으로 정규화 오차 10%를 넘는 점의 영향을 줄이는 과정을 10번 반복한다. `c0`은 실행 고정 비용을 받는 절편이며
선택 식에는 넣지 않는다. 이 w_t는 2단계에서 w_t가 끌려가는 기준이다.

### 7.2 2단계: 선택 손실로 모든 상수 맞추기

학습 카테고리의 측정에서 **선택 손실**이 가장 작아지도록 상수를 한꺼번에 맞춘다. 실행 시간을 정확히 예측하는 것이 아니라
형상마다 빠른 조합을 고르는 것이 목적이기 때문이다.

- **선택 손실:** 형상마다 "식이 고른 조합의 실측 시간 ÷ 실측 최선 − 1"이다. split 1에 reduce가 있는 경우(epilogue 있는 층)와
  없는 경우를 따로 세어 함께 평균한다. 형상 하나의 손실은 30%에서 자른다.
- **매끄러운 근사로 최적화한다:** 비용이 가장 작은 조합 하나만 고르면 손실이 상수에 대해 계단 모양이라 최적화가 안 된다.
  그래서 비용이 비슷한 조합들에 확률을 나눠 주는 softmin(온도 0.01)으로 기대 손실을 구해 최소화한다. 평가에서는 원래대로 하나만 고른다.
- **w_t를 기준값 쪽으로 끈다:** 기준 타일(128 × 128)을 뺀 w_t의 로그 비율 제곱합에 0.1을 곱해 더한다. 이 끌림이 없으면 w_t가
  학습 형상의 우연한 순서에 맞춰져 처음 보는 형상에서 나빠진다. 128 × 128의 w_t는 기준값으로 고정한다. 모든 w_t를 같은 비율로
  바꿔도 선택은 같기 때문이다.
- **최적화 방법:** Nelder-Mead를 세 시작점에서 돌려 가장 좋은 결과를 쓴다.

학습 형상에서는 측정한 후보끼리만 비교한다. gridsplit · split처럼 일부 타일만 잰 형상은 그 안에서만 고른다.

## 8. 평가와 채택 기준

`fit.py`의 출력:

- **val · val2 선택 손실:** split 1의 reduce 없음 · 있음 두 경우를 함께 센 평균
- **test 선택 손실:** 층별 실제 epilogue 조건(`as the layer`)을 적용한 평균
- **pi0.5 추론 1회의 Linear 합:** 실측 최선과 식이 고른 조합의 합(호출 수 가중, 층별 epilogue 반영)
- **`linear.h`에 넣을 상수**
`pi0.5 Linear per inference`는 개별 커널 측정 시간을 호출 수로 가중해 더한 추정치이며, 데모 전체 추론을 직접 잰 값은 아니다.

채택 기준(모두 만족):

- **test 층별:** 평균 손실 3% 이하
- **val · val2:** 각각 평균 손실 3% 이하
- **pi0.5 Linear 합:** 실측 최선 대비 5% 이내

현재 상수의 결과는 val 0.24%, val2 1.13%, test 0.42%, pi0.5 Linear 합 +0.5%다.

기준을 넘지 못하면 원인을 어디로 보느냐에 따라 둘 중 하나를 고른다.

- **a. 샘플이 문제일 때:** 샘플 수를 늘리거나 샘플 분포를 바꾼다. 5 → 6 → 7 → 8을 반복한다.
- **b. 비용 식이 문제일 때:** 3절의 비용 식만 다시 설계하고 측정 데이터는 그대로 쓴다. 3 → 7 → 8을 반복한다.

샘플 수는 보통 충분히 크게 잡으므로, b를 반복해 비용 식을 정교하게 다듬는 것이 핵심이다. 다만 새 비용 식에 맞춰 샘플 분포를
바꿔야 할 때는 3 → 5 → 6 → 7 → 8을 반복한다.

보정 대상이 바뀔 때는 다음을 따른다.

- **타일 후보가 바뀌면:** 5 → 6 → 7 → 8을 반복한다.
- **커널이 바뀌면:** 비용 식 재설계부터 시작해 3 → 5 → 6 → 7 → 8을 반복한다.

## 9. 비용 모델을 Linear에 이식

8절의 기준을 통과하면 확정한 상수를 실제 Linear의 선택 코드로 옮긴다. 수정할 파일은
[vai/nodes/linear.h](../../vai/nodes/linear.h) 하나다. Linear가 실행 때 타일과 split을 고르는 전체 흐름은 부록 C에 있다.

### 9.1 보정 결과를 넣는 곳

`fit.py` 출력 마지막의 `constants for the f16 candidate table / intelTileParams (Linear)`를 사용한다.
1단계의 w_t는 2단계의 기준값일 뿐이므로 쓰지 않는다.

| 보정 결과 | `fit.py` 출력 이름 | 반영 위치 |
|---|---|---|
| 타일별 w_t | `waveTime (us)` | `kIntelF16Acc`의 `waveTime` |
| floor | `floor` | `intelTileParams`의 `floor`(fp16 누적 쪽, `accF32`가 거짓일 때) |
| τ | `tail` | `tail`(fp16 누적 쪽) |
| ε | `wholeWaves` | `wholeWaves` |
| β | `inputReread` | `inputReread` |
| π_in, π_out | `reducePenalty in L2 / past L2` | `reduceInL2`, `reducePastL2` |
| 후보 타일 | | 후보를 바꿨다면 `kIntelF16Acc`의 `wgSize, tM, tN, sgn, wgK`와 순서를 맞춘다 |

- **단위:** w_t 출력은 µs이고 코드도 µs다. 나머지는 무차원이다. 변환 없이 넣는다.
- **절편:** `c0`은 측정값을 맞추기 위한 절편이므로 코드에 옮기지 않는다.
- **기준 타일:** `refWave`는 `kIntelF16Acc[3]`(128 × 128)를 가리킨다. 후보 순서가 바뀌면 이 인덱스도 바꾼다.
- **GPU L2 크기:** `l2Bytes`(4 MB)는 공식 스펙 값이다. 다른 GPU에서는 그 GPU의 값으로 바꾼다.

### 9.2 스크립트와 코드가 같은 식을 쓰는지 확인

`fit.py`의 `cost()`와 `linear.h`의 `intelTileParams()`는 같은 후보에 같은 비용을 계산해야 한다.
3절의 식을 바꿨다면 상수만 옮겨서는 안 되고, 바뀐 항과 조건도 함께 옮긴다.

| 확인 항목 | 두 구현에서 같아야 할 것 |
|---|---|
| 하드웨어 값 | 코어 수, 코어당 HW스레드 수 |
| 연산 비용 | 타일 수의 올림, `per`, `cap`, `full`, `rem`, `load`(마지막 웨이브 직선), split별 K 길이 |
| 꼬리와 정수 웨이브 | τ를 더하는 조건(full ≥ 1), ε를 더하는 조건(full ≥ 2 그리고 rem = 0) |
| I 다시 읽기 | β 항의 I 크기(M × ks × I 바이트)와 GPU L2 크기 |
| reduce 비용 | π 항의 계산식, π_in · π_out을 가르는 조건(M·N·s·4 B ≤ L2), 실행 조건(split 2 이상, 또는 split 1이면서 epilogue) |
| 후보 범위 | 타일 목록, split 목록, K / s ≥ 64 제한 |
| 동점 처리 | 후보 순회 순서와 비용이 같을 때 남는 조합 |

측정 스크립트는 partial이 1 GiB를 넘는 split을 측정에서 빼지만, `intelTileParams()`에는 이 제한이 없다.
그런 형상에서는 코드가 측정하지 않은 조합을 고를 수 있으므로 9.3절에서 따로 확인한다.

## 부록 A. 타일 후보 목록 구성하기

이 절은 비용 모델이 비교할 타일 후보 목록을 만드는 기준과 절차를 설명한다. 2절의 표는 타일 크기마다 실행 설정 하나를
대표로 정해 구성한 목록이다.
기존 후보를 그대로 보정할 때는 이 절차를 수행할 필요가 없다.

### A.1 타일을 정하는 네 값

타일은 네 값으로 정한다. 커널은 subgroup 크기 16(SIMD16)으로 고정한다.

| 값 | 뜻 |
|---|---|
| wgSize | 워크그룹의 invocation 수. subgroup 수는 wgSize / 16 |
| SGN | N 방향으로 놓는 subgroup 수. 나머지 (wgSize / 16) / SGN개는 M 방향으로 쌓인다 |
| tM | subgroup 하나가 맡는 출력 행 수. subgroup의 16 lane이 같은 행들을 나눠 가진다 |
| tN | lane 하나가 맡는 출력 열 수. 열은 16칸 간격(lane, lane + 16, …)으로 잡는다 |

이 넷에서 타일 크기, 동시 실행 수, 레지스터 사용량이 나온다.
```
wgM = (wgSize / 16) / SGN × tM          M 방향 subgroup 수 × subgroup당 행
wgN = SGN × 16 × tN                     N 방향 subgroup 수 × lane 16 × lane당 열
cap = 128 / (wgSize / 16)               코어당 HW스레드 128 ÷ 워크그룹당 HW스레드(= subgroup 수)
누산기 = tM × tN                         lane마다 레지스터에 쥐는 출력 개수
W 캐시 = tN × wgK                        lane마다 k 블록 하나 동안 레지스터에 두는 W 값 개수
```

예를 들어 32 × 32는 wgSize 128(subgroup 8개), SGN 1이다.
- **M 방향:** subgroup 8개 × tM 4 = 32행이다.
- **N 방향:** lane 16개 × tN 2 = 32열이다.
- **lane당 레지스터:** 누산기 4 × 2 = 8개, W 캐시 2 × 8 = 16개를 쥔다.

### A.2 대표 설정을 고르는 기준과 절차

**같은 크기를 만드는 조합은 여럿이다.** 32 × 32만 해도 (wgSize 128, tM 4, tN 2, SGN 1) 말고 (64, 8, 2, 1), (128, 8, 1, 2) 등이
있다. 조합마다 동시 실행 수, lane당 레지스터, 공유 메모리 접근 모양이 달라 속도가 다르다. 그래서 크기마다 측정으로 가장
빠른 조합 하나를 대표로 정해 후보 표에 둔다. 2절의 표가 그 대표들이다.

새 타일 크기를 후보에 추가하거나 기존 타일의 대표 설정을 바꿀 때는 다음 절차를 따른다.
GPU 세대나 커널이 바뀐 경우에도 이 절차로 기존 대표 설정을 다시 검토한다.

1. **조합 나열:** 타일 크기마다 같은 크기를 만드는 (wgSize, tM, tN, SGN) 조합을 나열한다
   (탐색 범위: wgSize 128 · 256 · 512, SGN 1 · 2).
2. **레지스터 예산 확인:** lane당 누산기와 W 캐시의 합이 256 B를 넘는 조합은 제외한다.
   256 B는 HW스레드 하나의 레지스터(128 GRF, 4 KB)를 SIMD16의 16 lane으로 나눈 몫이다.
   128 × 128 타일은 fp16 누산기 64개와 W 캐시 64개로 (64 + 64) × 2 B = 256 B여서 한도에 딱 닿는다. 실제 spill 여부는 다음 단계에서 확인한다.
3. **컴파일 결과 확인:** 하네스에 `-stats`를 붙여 SIMD 폭과 scratch 크기를 확인한다.
   SIMD16이며 scratch가 0인 조합만 남긴다. scratch는 레지스터에 담지 못한 값을 메모리로 내보내는 spill의 지표다.
4. **속도 비교:** 해당 타일 크기가 쓰일 대표 형상 몇 개에서 `-passes 9 -flush`로 번갈아 측정해,
   가장 빠른 조합을 그 크기의 대표 설정으로 정한다.
5. **목록 갱신:** 대표가 바뀌면 2절의 후보 표와 `run.py`의 `TILES`를 함께 고치고, 5절부터 측정과 보정을 다시 한다.
   `fit.py`는 `run.py`의 `TILES`를 읽는다.

### A.3 후보 몇 개를 어떤 크기로 둘지 고르기

후보 크기는 넓은 풀을 측정해 고른다. 비용 모델은 쓰지 않는다. [calib/pool.py](calib/pool.py)가 세 단계를 맡는다.

1. **풀 만들기와 대표 설정(`pool.py rep`):** wgM · wgN을 {32, 48, 64, 96, 128, 192, 256}에서 골라 만든 49개 크기 중, A.2의 레지스터 예산
   안에서 만들 수 있는 46개가 풀이다. 크기마다 모든 설정을 대표 형상 6개에서 split 1로 재서, scratch 0 · SIMD16 · 오차 기준을
   통과한 설정 중 가장 빠른 것을 대표로 둔다.
2. **풀 측정(`pool.py measure`):** 대표 설정 전부를 split 1 ~ 16으로, M · N 16 단위 무작위 형상 50개에서 잰다.
3. **고르기(`pool.py select`):** 형상마다 크기별 최선 시간을 구하고, "고른 후보 안의 최선 ÷ 풀 전체의 최선 − 1"의 평균을 손실로 둔다.
   풀 전체에서 시작해 손실이 가장 적게 느는 크기를 하나씩 빼고, 매번 안팎 하나씩 바꿔치기로 다듬는다. 5개 이하는 전수 탐색으로
   확인한다. 하나를 더 넣어도 평균 손실이 1%p 넘게 줄지 않는 개수에서 멈춘다.

f16 누적에서는 192 × 192가 spill로 빠져 45개 크기를 쟀고, 5개(32 × 64, 64 × 96, 96 × 128, 128 × 128, 192 × 64)에서 멈췄다.
풀 전체 최선 대비 평균 손실은 2.2%다. 이 측정은 partial 버퍼를 공유하기 전의 하네스와 M · N 128 단위 형상으로 한 것이라,
다시 할 때는 고친 하네스와 16 단위 형상(`pool.py`의 기본값)으로 한다.

## 부록 B. 측정 조건과 모델의 한계

- **코어 수는 공식 스펙으로 맞춘다:** Meteor Lake는 7코어와 8코어 SKU의 장치 ID가 같고(0x7D55), 드라이버가 코어 수를 알려
  주지 않는다. 코어 수가 틀리면 웨이브 계산 전체가 어긋난다.
- **측정 조건과 실제 조건을 맞춘다:**
  - **캐시:** 매 실행 GPU L2를 비우는 것은 층마다 다른 가중치를 읽는 모델의 조건이다. 같은 W를 반복해서 읽으면 W가
    GPU L2에 남아, 작은 형상이 실제보다 빠르게 측정된다.
  - **커널:** 타일 커널은 Linear의 셰이더와 본문이 같은 `linear-tile-11.comp`, reduce 패스는 Linear의 reduce와 같은 방식으로 접는 `split-reduce.comp`를 쓴다(4.2절).
- **측정 도구의 메모리:** 한 번의 실행에 split 설정이 여러 개이고 출력이 크면, 설정마다 따로 만든 partial 버퍼가 수 GB가 되어
  측정이 왜곡된다. 하네스는 형상마다 partial 버퍼 하나를 공유한다(4.2절). 이전 하네스로 잰 데이터는 출력이 큰 형상의 split 시간을
  믿을 수 없다.
- **형상 분포의 편향:** M · N을 128의 배수로만 뽑으면 128 폭 타일만 패딩이 없어 유리하게 측정된다. 학습 · 평가 형상은 16 단위로 뽑는다.
- **작은 형상:** 실행이 0.5 ms 안팎인 작은 형상에서는 고정 오버헤드가 커서 웨이브 모델이 거칠다. 손실 비율은 커도 잃는 시간은 작다.
- **상수는 기기 세대마다 다시 맞춘다:** 타일 간 w 비율, floor, τ, π는 Xe-core 구조에서 나오는 값이다. 다른 세대(Xe2 등)나
  외장 GPU에서는 이 절차로 다시 맞춘다.

## 부록 C. Linear가 타일과 split을 고르는 흐름

`Linear::prepare()`는 형상 (M, N, K)가 정해질 때마다 다음 순서로 커널과 파라미터를 정한다.

1. **커널 갈래:** M이 8 이하이면 slab 커널을 쓰고, 그 외에는 타일 커널을 쓴다. 이 문서는 타일 커널만 다룬다.
2. **Intel 경로 진입(`useIntelTile`):** ggml이 고른 기본 타일 대신 `linear-tile-intel.comp`를 쓸지 정한다.
3. **후보 표 선택:** 누적 dtype과 I · W dtype에 따라 후보 타일 표 하나를 고른다.
4. **비용 비교(`intelTileParams`):** 후보 타일 × split마다 3절의 비용 식을 계산해 가장 싼 조합을 고른다.
   비용이 같으면 먼저 계산한 조합(표의 앞쪽 타일, 작은 split)이 남는다.
5. **나머지 파라미터:** wgK, splitSize, 워크그룹 실행 순서를 정하고 디스패치한다.

전체 결정 트리는 다음과 같다.

```
Linear::prepare (M, N, K)
│
├─ ⓪ 커널 갈래
│   M ≤ 8 ─────────────────────────────────────▶ slab 커널 (이 문서 대상 아님)
│   그 외 ▼ 타일 커널
│
├─ ① 진입: useIntelTile
│   Intel GPU? ─ 아니오 ─────────────────────────▶ 기존 ggml 경로
│   ggml이 coopmat을 골랐나(tK≠0)? ─ 예 ─────────▶ 기존 ggml 경로
│   subgroup 16을 고정할 수 있나? ─ 아니오 ───────▶ 기존 ggml 경로
│   fp32 누적이면서 M < 256? ─ 예 ──────────────▶ 기존 ggml 경로
│   │ (fp32 누적 = accDtype fp32 이거나, I·W가 둘 다 fp32라 fp32로 스테이징)
│   ▼
│   linear-tile-intel 사용
│
├─ ② 후보 표 선택
│   fp16 누적 ────────────▶ kIntelF16Acc          split 1·2·4·8·16 함께 탐색
│   │                       32×64, 64×96, 96×128, 128×128, 192×64
│   fp32 누적, W fp16 ────▶ kIntelF32AccF16Stage  split 1 고정
│   │                       32×64, 128×48
│   I·W 둘 다 fp32 ───────▶ kIntelF32AccF32Stage  split 1 고정
│                           64×32, 128×48
│
├─ ③ 후보 × split 마다 비용을 계산해 최솟값 선택
│   tiles = ⌈M/wgM⌉·⌈N/wgN⌉
│   per   = ⌈tiles·s / cores⌉            가장 바쁜 코어가 맡는 WG 수 (cores: 드라이버 값, 모르면 8)
│   cap   = 128 / (wgSize/16)            코어당 동시 WG 수 (wg128→16, 256→8, 512→4)
│   full  = ⌊per/cap⌋,  rem = per mod cap,  r = rem/cap,  ks = ⌈K/s⌉
│   fp16 누적 (3절의 식):
│     load = full + (rem > 0 ? floor + (1−floor)·r : 0)
│     work = ks·(load + τ·[full ≥ 1] + ε·[full ≥ 2, rem = 0]) · (1 + β·max(0, log2(M·ks·4B / L2)))
│     cost = w_t·work + (s > 1 이거나 epilogue면) π·w_128×128·M·N·(s+1)/4096,  π = M·N·s·4B ≤ L2 ? π_in : π_out
│     상수: floor 0.485, τ 0.127, ε 0.400, β 0.077, π_in 0.420, π_out 0.894, L2 4 MB
│     w_t (µs): 32×64 0.189, 64×96 0.396, 96×128 0.365, 128×128 0.434, 192×64 0.232
│   fp32 누적: load = full + (rem > 0 ? max(r, 0.5) : 0),  cost = w_t·(ks·load + 8·per), split 1만
│   s > 1은 K/s ≥ 64일 때만 시도
│
├─ ④ 나머지 파라미터
│   wgK        = K % 후보 wgK == 0 ? 후보 wgK(8 또는 4) : 4
│   splitSize  = 사용자가 지정했으면 그 값
│                아니면 s > 1 일 때 ⌈⌈K/s⌉ / wgK⌉·wgK, s = 1 이면 K
│   splitCount = ⌈K / splitSize⌉
│   순서 nFirst = wgM·sizeof(I) > wgN·sizeof(W)
│      예  ▶ N 우선 (x축에 M 타일, 같은 I 공유)
│      아니오 ▶ M 우선 (같은 W 공유, 동점도 M 우선)
│
└─▶ dispatch (nFirst ? (tilesM, tilesN) : (tilesN, tilesM)) × splitCount
    splitCount > 1 이거나 epilogue가 있으면 reduce 패스(linear-reduce) 추가
```

- **epilogue:** bias, residual, 활성화, 1이 아닌 scale 중 하나라도 있으면 참이다. 타일 커널은 epilogue를 처리하지 않으므로
  이때는 split 1이어도 reduce 패스가 돈다. ③의 reduce 항 조건과 실제 reduce 실행 조건(`needReducePass`)은 같은 조건이다.
- **fp32 누적 경로:** 이 보정의 대상이 아니다. split을 탐색하지 않고 reduce 항도 계산하지 않는다.
- **요청 split과 실제 split:** ④에서 K 조각을 wgK 단위로 올리므로 `splitCount`가 요청한 s보다 작을 수 있다.

## 부록 D. 비용 식의 버전별 변화 (fp16 누적)

기호는 3.1절과 같다. `ks = ⌈K/s⌉`, `r = rem / cap`, `w_ref`는 128 × 128의 w_t, `[조건]`은 참이면 1이다.

| 항목 | v2 | v4 | v5 | v6 (현재) |
|---|---|---|---|---|
| 후보 수 | 7 | 7 | 5 | 5 |
| 덜 찬 마지막 웨이브 | max(r, 0.6) | max(r, 0.65) | max(r, 0.65) | 0.485 + 0.515 r |
| 꼬리 | 없음 | τ 0.2 | τ 0.05 | τ 0.127 |
| 정수 웨이브 | 없음 | 없음 | 없음 | ε 0.400 |
| I 다시 읽기 | 없음 | 없음 | 없음 | β 0.077 |
| partial 저장 | w_t × per × 면적 / 4096 | 없음 | 없음 | 없음 |
| reduce | 10 µs × M·N/10^6 × (s+1), split 2 이상만 | π 0.3 × w_ref × M·N(s+1)/4096, epilogue 포함 | π 0.375 | π 0.420 / 0.894 (GPU L2 안 / 밖) |
| 상수 맞추는 기준 | w_t: 시간 손실. 나머지는 기록 없음 | 모두 시간 손실 | w_t · π: 시간 손실<br>floor · τ: 선택 손실(평탄 구간) | 모두 선택 손실 |

상수를 맞출 때 무엇을 줄이느냐에 따라 두 가지로 나뉜다.

- **시간 손실:** 측정한 조합 하나하나에 대해 식이 낸 비용과 실측 시간이 얼마나 다른지를 잰다. 보통 상대 오차
  `|예측 ÷ 실측 − 1|`을 모든 조합에 걸쳐 평균하거나 제곱해 더하고, 이 값이 가장 작은 상수를 고른다. 식이 **시간을 맞히게** 만드는
  기준이다. 예를 들어 형상 하나에 조합 A(1.00 ms)와 B(1.10 ms)가 있을 때, 식이 A를 1.05, B를 1.02로 예측하면 두 조합의 오차는 각각
  5%, 7%로 작지만 순서는 뒤집혀 B를 고른다.
- **선택 손실:** 형상마다 식이 비용이 가장 작다고 고른 조합의 실측 시간이 그 형상의 실측 최선보다 얼마나 느린지
  `고른 조합의 실측 ÷ 실측 최선 − 1`을 재고, 형상에 걸쳐 평균한다. 식이 **빠른 조합을 고르게** 만드는 기준이다. 위 예에서
  선택 손실은 1.10 ÷ 1.00 − 1 = 10%다. 반대로 예측 시간이 크게 틀려도 A가 가장 싸다는 순서만 맞으면 선택 손실은 0이다.

Linear가 실제로 하는 일은 고르는 것이므로, 목적에 맞는 기준은 선택 손실이다. 다만 선택 손실은 상수를 조금 바꿔도 고르는
조합이 그대로이다가 어느 순간 바뀌는 계단 모양이라 최적화가 어렵고, 학습 형상의 우연한 순서에 맞춰지기 쉽다. v5는 floor · τ만
선택 손실이 가장 작은 영역의 가운데(평탄 구간)에서 골라 이를 피했고, v6는 비용이 비슷한 조합들에 확률을 나눠 주는 매끄러운
근사로 모든 상수를 맞추되 w_t가 시간 손실로 맞춘 값에서 멀어지지 않게 끈다(7.2절).

버전별 최종 식:

- **v2:** `cost = w_t · ks · (full + max(r, 0.6)) + [s > 1] · (w_t · per · wgM · wgN / 4096 + 10 µs · M·N/10^6 · (s+1))`
- **v4:** `cost = w_t · ks · (full + max(r, 0.65) + 0.2 · [full ≥ 1]) + [s > 1 또는 epilogue] · 0.3 · w_ref · M·N·(s+1) / 4096`
- **v5:** v4와 같은 식에 후보 5개, `τ 0.05`, `π 0.375`.
- **v6:** `cost = w_t · ks · (full + 0.485 + 0.515 r + 0.127 · [full ≥ 1] + 0.400 · [full ≥ 2, rem = 0]) · (1 + 0.077 · max(0, log2(M · ks · 4 B / 4 MB)))`
  `+ [s > 1 또는 epilogue] · π · w_ref · M·N·(s+1) / 4096`, `π = M·N·s·4 B ≤ 4 MB ? 0.420 : 0.894`.
  덜 찬 마지막 웨이브 항(0.485 + 0.515 r)은 rem > 0일 때만 더한다.

### D.1 v2 대비 v6가 빨라진 원인

셰이더 효과와 선택 효과를 나누려고, v2 실행 파일에 W 패딩 0 셰이더를 붙인 "v2 + 패딩 제거"를 함께 쟀다. 셰이더는 실행 때
`build/shaders`에서 읽고, v2와 지금 셰이더의 차이는 fp16 스테이징의 W 패딩 한 줄(1칸 → 0)뿐이다. 세 실행 파일을 라운드마다 순서를

## 부록 E. pi0.5 층별 최선 설정

pi0.5의 Linear 층마다, `linear-tile-intel.comp`의 fp16 누적 경로에서 쓸 수 있는 설정 중 가장 빠른 조합 1 ~ 5위를 측정으로
정리한다. 설정은 (타일 크기, wgSize, tM, tN, SGN)과 split 수의 조합이다.

### E.1 측정 조건

- **설정:** wgM · wgN이 {32, 48, 64, 96, 128, 192, 256}인 크기 중 lane당 레지스터 256 B 안에서 만들 수 있고, spill이 없으며(scratch 0)
  SIMD16으로 컴파일되는 설정 191개다(부록 A).
- **split:** 1, 2, 4, 8, 16. split 하나의 K가 64 미만이 되거나 partial이 1 GiB를 넘는 split은 뺐다.
- **epilogue:** 층마다 실제 조건을 따른다. epilogue가 있는 층은 split 1도 reduce 패스를 거친 시간이다.
- **측정:** 하네스(`test-linear-tune-intel`)의 `linear-tile-11.comp` · `split-reduce.comp`, `-passes 9 -flush`. 한 층의 모든 조합을 9바퀴
  번갈아 재고, 바퀴마다 GPU L2를 비운 실행 R회(층마다 3 ~ 16)의 평균을 낸 뒤 바퀴 1 ~ 8의 중앙값을 쓴다.
- **세션:** 2026-10-24 한 번. 원본은 `build/pi05-pool191/pi05.out`.
- **읽는 법:** 시간은 커널 단독 시간이라 데모 프로파일의 층별 시간보다 크다. 1위와 아래 순위의 차이가 2 ~ 3% 안이면 측정 잡음과 구별하기 어렵다.
